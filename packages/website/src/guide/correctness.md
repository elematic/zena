Zena treats correctness as a machine problem first and a human review problem
second. Whether code is written by a person or generated by an AI agent, every
invariant the compiler or runtime can check automatically is one less failure
mode a reviewer has to spot by reading source line by line.

## What "sound" means

A static type system is **sound** when a well-typed expression cannot produce a
value at runtime that contradicts its static type. If a binding has type
`Account`, evaluating it yields an `Account` instance—never `null`, never an
uninitialized shell whose fields have not been written yet, and never an
unrelated record cast through an unchecked assertion.

Soundness matters for two audiences at once:

- **Programmers and reviewers**: When a function accepts `items: FixedArray<User>`,
  neither the implementation nor a reviewer needs to guard against `null` arrays,
  missing fields, or non-`User` elements slipped in through covariance.
- **The compiler**: Because static types match runtime representations, Zena
  emits direct WebAssembly GC `struct.get` and `array.get` instructions and
  unboxed primitive locals (`i32`, `f64`) without defensive type tags or fallback
  paths.

## Where TypeScript gives up soundness

TypeScript's type system was designed to model existing JavaScript idioms, so it
deliberately trades soundness for ergonomics and gradual adoption in several
places:

- **`any` and unchecked assertions (`as T`)**: `any` disables checking across
  every expression it touches, and `value as Account` changes the static type
  without emitting a runtime check.
- **Covariant mutable arrays**: `Array<Cat>` is assignable to `Array<Animal>`, so
  a helper taking `Array<Animal>` can push a `Dog` into a caller's `Array<Cat>`.
- **Method parameter bivariance**: Method syntax (`method(x: Cat): void`) allows
  unsafe parameter narrowing across subtypes.
- **Unchecked index access**: Reading `items[i]` or `map[key]` yields `T` by
  default even when the index is out of bounds (`undefined` at runtime).
- **Dynamic object shapes and coercion**: Objects can gain or lose properties at
  runtime, and operators coerce operands implicitly (`"1" + 1` produces `"11"`,
  and `0` or `""` are falsy in `if` conditions).

Each escape hatch is convenient in isolation, and together they mean a TypeScript
type annotation is an advisory hint rather than an enforceable guarantee.

## What Zena does instead

Zena keeps TypeScript's surface readability while closing those soundness gaps:

- **No `any` escape hatch**: There is no universal `any` type that disables the
  checker. `anyref` is the top type for garbage-collected references only, and
  recovering a concrete type from `anyref` requires a runtime `is` test or a
  checked `as` cast.
- **Non-nullable by default**: `String` never holds `null`; nullable references
  are spelled `String | null` and must be narrowed with `!= null`, `?.`, `??`, or
  pattern matching before use.
- **Checked `as` casts**: `expr as Target` compiles to a WebAssembly GC checked
  cast (`ref.cast`) for reference types or an explicit numeric conversion for
  primitives. An invalid reference cast traps immediately at the cast site instead
  of corrupting downstream state.
- **Invariant mutable generics**: Generic classes and mutable arrays such as
  `FixedArray<T>` and `GrowableArray<T>` are invariant in `T`, preventing subtype
  aliasing from writing the wrong element type into a container.
- **Two-phase constructor initialization**: Every field must be initialized in
  its declaration or in the constructor's `: ...` initializer list before `this`
  becomes readable in the constructor body, ruling out partially initialized
  objects.
- **Exhaustive `match` and strict booleans**: `match` expressions over `sealed`
  hierarchies, enums, booleans, and unions must cover every case at compile time,
  and `if`/`while` conditions require an explicit `boolean`.
- **Distinct and opaque types**: `distinct type UserId = i32` creates a zero-cost
  nominal type that cannot be mixed accidentally with `OrderId` or raw `i32`
  counters.

```zena
distinct type Cents = i32;

sealed class Payment {
  case Card(last4: String, amount: Cents)
  case Cash(amount: Cents)
}

function amountOf(payment: Payment): Cents {
  // Adding a new case to `Payment` turns every incomplete `match` into a compile error.
  return match (payment) {
    case Card {amount}: amount
    case Cash {amount}: amount
  };
}
```

## Contracts and the verification spectrum

Static types check the shapes of values, while many bugs live in relationships
between values: a withdrawal exceeding an account balance, a binary search index
drifting past `hi`, or a mutating method forgetting to update a count. Zena
addresses this with first-class [contracts](/guide/contracts/) positioned along a
gradual verification spectrum:

| Layer                         | Mechanism                                                          | What it guarantees                                                                       | Status          |
| :---------------------------- | :----------------------------------------------------------------- | :--------------------------------------------------------------------------------------- | :-------------- |
| **Sound static types**        | Non-nullability, exhaustive `match`, `distinct type`, checked `as` | Values match their declared representations on every path                                | **Implemented** |
| **Runtime contracts**         | `requires (...)`, `ensures (...)`, `invariant (...)`               | Domain pre/post-conditions and loop invariants fail fast with `ContractError`            | **In progress** |
| **Test/debug-only contracts** | `debug requires`, `debug ensures`, `debug invariant`               | Expensive $O(n)$ checks run in `zena test` and `--debug` (`-g`), omitted in plain builds | **Implemented** |
| **Static verification**       | `@verify`, `ghost` clauses, SMT solver                             | Compiler proves contracts hold for all possible inputs at compile time                   | **Planned**     |

### Runtime and debug contracts today

`requires`, `ensures` (with `result` and `old(...)`), and loop `invariant`
clauses attach directly to function signatures and loop headers. Unmarked
clauses run unconditionally in every build and throw a `ContractError` with the
failed clause text when violated, while clauses prefixed with `debug` run under
`zena test` and `--debug` (`-g`) builds and emit zero code in ordinary builds:

```zena
class BoundedCounter {
  var value: i32;
  limit: i32;

  new(this.value, this.limit)
    requires (0 <= value && value <= limit);

  add(delta: i32): i32
    requires (delta > 0)
    requires (this.value + delta <= this.limit)
    ensures (this.value == old(this.value) + delta)
    ensures (result == this.value)
  {
    this.value += delta;
    return this.value;
  }
}
```

Unmarked `requires` clauses also feed Zena's control-flow type narrower: writing
`requires (text != null)` or `requires (pet is Cat)` refines the parameter type
throughout subsequent clauses and the function body. By contrast, `debug requires`
clauses do not narrow types because ordinary builds execute the body without
running `debug` checks.

Contracts already work on functions, closures, methods, constructors, and
`while`/`for`/`for-in` loops. Clauses on generators, bodyless interface/abstract
methods, and `ensures` on `async` functions and `inline` returns are still being
completed (and are rejected at compile time rather than silently skipped).

### Toward static proofs

Future versions plan to pass contracts and loop invariants to an SMT solver
(following the Dafny and SPARK model) for functions opted in with `@verify`,
alongside specification-only `ghost` clauses and quantifiers erased at compile
time. See [Contracts](/guide/contracts/) and the
[Contracts Design](/development/design/contracts/) document for details.

## Memory safety without a borrow checker

Zena separates memory safety from external resource lifecycles so ordinary data
structures do not pay the ergonomic cost of pervasive lifetime annotations:

- **Garbage-collected memory**: Classes, records, strings, closures, and arrays
  live on the WebAssembly GC heap. The host engine's collector reclaims
  unreachable objects, and WebAssembly's typed heap references and bounds-checked
  arrays prevent out-of-bounds reads, type confusion, and dangling pointers
  without `unsafe` blocks.
- **Affine ownership for external handles**: File descriptors, sockets, WASI
  Component Model handles, and linear-memory buffers require deterministic
  release. Zena tracks these with `using` declarations and `resource class`
  handles (`Own<T>` and stack-bound `Borrow<T>`). Because borrows cannot be
  stored in heap fields, the compiler checks ownership locally without lifetime
  parameters on structs or functions. See
  [Resources and Ownership](/guide/resources/).

## The cost of soundness

Soundness asks for explicit work at boundaries where dynamic or unsound languages
allow shortcuts:

- **External data must be decoded**: JSON payloads, network bytes, and host
  inputs cannot be cast to typed records with `as MyRecord`; they are parsed and
  validated into typed values at the boundary.
- **Explicit numeric conversions**: Mixing `i32`, `i64`, and `f64` requires
  explicit `as` conversions, and `/` always performs floating-point division
  (integer division uses `div(a, b)` from `zena:math`).
- **Up-front initialization**: Cyclic object graphs or delayed setup use explicit
  `T | null` fields or factory helpers because constructors cannot expose `this`
  before every field has an initial value.
- **Container invariance**: Functions that only read elements from a collection
  accept read-only interfaces (such as `Sequence<T>` or `Iterable<T>`) rather
  than mutable `GrowableArray<T>`.

In return, once values cross into typed Zena code and pass a function's
`requires` clauses, both the compiler and human readers can rely on what the
signature says.
