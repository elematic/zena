# workspace-hack

A crate with no code that every crate in the Cargo workspace depends on,
so that `zena-run`, `zena-cli` and `zfx` share one build of wasmtime and
Cranelift. It is generated by [cargo hakari](https://docs.rs/cargo-hakari)
and is not published.

## Why it exists

Cargo resolves features per command. `cargo build -p zena-run` turns on
the features `zena-run`'s dependency tree asks for, and
`cargo build -p zenafx` turns on the ones `zenafx`'s asks for. When a
crate both trees share gets different features, cargo builds it twice,
and it builds everything above it twice too, since an artifact's hash
covers the features of everything beneath it. wasmtime and Cranelift are
above almost everything.

zenafx's graphics stack asks for more features of about twenty crates the
other binaries also use (`futures`, `hashbrown`, `rustix` and the `icu`
crates among them), so it compiled its own wasmtime. Before that,
`zena-run`'s logger turned on `log`'s `std` feature and `zena-cli`'s
dependencies did not, which gave `zena-cli` its own copy as well.

This crate depends on each of those shared crates with the union of the
features the workspace asks for. Every member depends on it, so every
command resolves the same features. From an empty target directory, on 16
CPUs, building the three binaries one after another took 248s before and
176s after.

## After changing a Rust dependency

Run, from the repository root (both are in the dev shell):

```bash
cargo hakari generate      # rewrites the HAKARI SECTION of Cargo.toml
cargo hakari manage-deps   # adds workspace-hack to a crate that lacks it
```

and commit what they change, along with `Cargo.lock`. CI runs both with
`--diff` and `--dry-run` and fails when either would change something. A
stale crate still builds, with a second copy of wasmtime, so nothing else
would catch it.

The settings, including the platforms whose target-specific dependencies
are unified, are in [`.config/hakari.toml`](../../.config/hakari.toml).

## Checking that it works

```bash
cargo hakari verify
cargo hakari explain futures   # which members ask for which features
```

To see the sharing itself, ask cargo which wasmtime each binary links:

```bash
for p in zena-run zena-cli zenafx; do
  cargo build --release -p $p --message-format=json |
    jq -r 'select(.reason=="compiler-artifact" and .target.name=="wasmtime") | .filenames[] | select(endswith(".rlib"))'
done
```

All three should print the same `libwasmtime-<hash>.rlib`.
